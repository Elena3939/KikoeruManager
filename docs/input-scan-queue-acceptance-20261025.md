# 输入扫描队列本地验收记录

日期：2026-10-25。对应设计：[输入扫描队列与批次记录改造方案](input-scan-queue-design.md)。

## 实现结果

- 启动扫描先建立持久批次并返回扫描 ID；前端查询状态，不再等待整个输入目录处理完才收到响应。
- 目录发现、分卷归组、稳定观察与业务处理重叠。一个分卷组对应一个候选；稳定观察按到期时间采样，等待期间释放执行许可。
- PostgreSQL 保存批次、候选、源占用、交接与 outbox。先持久化再入引擎队列；派生任务同样持久交接，恢复时复用任务 ID。
- 同目录索引复用成员信息；源代次或成员变化使证据失效。源改名先记录计划，失败或中断后按真实文件状态恢复，不覆盖原始来源语义。
- 共享预检复用现有合集识别、字幕补配和查重规则。确认的问题提前进入问题队列，正常候选交给原任务引擎。
- 元数据按近端队列窗口预取，消费时校验证据；不提前改变任务执行进度。配置缩容取消尚未开始的超额预取，保留在途请求。
- 普通业务许可、解压并发、资源预算、稳定观察参数和步骤开关沿用设置页配置。保存、加载、重载触发通知；缩容不强杀在途操作，也不新增超额许可。
- 操作历史使用 schema_version=2，同时表达发现关闭、候选处理结束、业务执行结果。根候选统计包括派生任务、问题处置与后台源文件归档。
- 通知从持久账本结算；发现未关闭、任务 pending/processing/paused/waiting_retry 时不提前发送完成或待人工通知。数据库写入失败通过 outbox 重试；事件键去重。任务生成前失败也有批次失败通知。

“跳过问题作品”和“源文件已经归档”仍是两个状态。归档由既有后台执行器按设置调度；尚未移动、归档失败会保留对应事实，不以问题处置成功冒充源文件搬迁成功。

## 协调层基准

工具：[benchmark-input-scan.py](../tools/benchmark-input-scan.py)。仅允许名称以 `_benchmark` 结尾的隔离数据库；每次使用临时 schema，完成后清理。

输入为 100 个逻辑组：70 个单 ZIP、30 组各 3 卷的 7z，共 160 个文件。文件仅包含识别魔数和短测试内容，不是可实际解压的完整压缩包；不能反映压缩包字节读取或解压成本。

覆盖真实目录发现、归组、稳定采样、PostgreSQL 候选与任务交接。业务预检、执行器消费是模拟。并发 4，稳定检查 3 次，测试工具将采样间隔设为 0.1 秒；该间隔是基准参数，不是应用设置页默认值。三次顺序采样，未清理操作系统缓存。

| 样本 | 接受扫描请求 | 首次持久交接 | 扫描关闭 |
| --- | ---: | ---: | ---: |
| 1 | 0.1104 秒 | 0.5904 秒 | 13.4462 秒 |
| 2 | 0.0468 秒 | 0.2090 秒 | 12.2987 秒 |
| 3 | 0.0409 秒 | 0.2118 秒 | 12.9144 秒 |

`first_extract_seconds=null`，没有测量真实解压启动时间。没有改造前同机同输入对照，不能声称提速倍数，也不能将上述时间外推为生产承诺。

实际首个任务开始时间取决于：发现该候选的时间、组成员完整性、设置要求的稳定观察窗口、必要预检、数据库交接、已有任务积压与共享业务许可。首个解压开始还受实际解压许可和存储资源等待影响。流式处理消除了无关后续候选对首次交接的全批阻塞，但不会取消这些必要约束。
