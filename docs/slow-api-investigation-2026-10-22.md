# 线上慢请求调查与修复计划

调查日期：2026-10-22。范围：黄色 `status=200 slow=True` 日志及社团聚合浏览、下载状态轮询、任务中心摘要、库存统计等慢请求。本文记录调查证据、修复计划与本机实施结果，不授权发布、重启或修改线上数据。

社团分类已按用户要求排除；社团聚合浏览是读取虚拟社团目录，与批量分类文件不是同一操作。本次不修改分类、社团补全或 API 重命名流程。

## 结论与证据边界

- `200` 是 HTTP 成功，`slow=True` 是后端中间件计时超过阈值，二者并不矛盾。默认阈值为 500ms，计时围绕 `await call_next`，不能当成浏览器网络总耗时或完整流式响应耗时。
- 已确认社团聚合冷读存在全量计算瓶颈：返回第一页前，先加载并聚合所有作品位置。下载状态和任务中心摘要存在可明确定位的高成本读路径，但历史各环节耗时尚未被分段日志记录。
- `resource_budget` 是请求结束时的全局摘要；`database_write active=1 waiting=0` 不能证明该请求等待数据库锁。`context={}` 也不能用于归因。
- 多个轻接口同期变慢符合共享调度受阻的现象；同步 I/O 代码已经找到，但没有历史事件循环延迟样本，不能宣布它是全部慢请求的唯一原因。

## 按模块实施

### 第一批：补齐诊断并优化社团聚合冷路径

涉及 `library_circle_aggregation_service.py` 和对应路由。

1. 记录缓存命中/失效原因、索引版本、作品位置数量、读取索引/身份解析/聚合/分页耗时，使用 request_id 关联请求。
2. 在一次快照构建内复用 RJ 归一化结果、路径解析中间值及同社团身份对象，避免逐位置重复 JSON 编码社团键。先用同样数据的不带分析器基线对比收益。
3. 保留现有构建锁，测量并发等待；同索引版本只构建一次，不能把已有锁当成缺失功能重复实现。
4. 检查索引版本变化引发全量重建的频率。若消除重复计算后仍达不到目标，再按变更的库/路径维护聚合结果；持久化聚合需要单独设计迁移、初始化和版本一致性，不能直接凭 SQL group by 替换现有路径识别。
5. 将路由返回前同步调用的索引视图读取和库健康检查一并移出事件循环；避免主要聚合在线程里、尾部仍阻塞异步路由。

回归必须覆盖：同 RJ 多库/多路径、路径社团优先级、元数据补全、未知社团、搜索排序分页、移动/删除/重命名后的失效。不能延长 TTL 隐藏陈旧路径，也不能引入文件系统全库扫描。

### 第二批：下载状态轮询

涉及 `routes.py` 下载状态路由、任务序列化辅助函数、`redis_service.py`、任务引擎的只读访问入口。

目前 HTTP/百度状态路由是 `async def`，内部却同步扫描 `get_all_tasks()`，然后逐任务同步访问 Redis。单任务元数据合并与状态取值分别读取 runtime，造成重复 GET；终态任务也先查再判断是否应用。compact 模式在全文件合并/清洗后才截断，不能降低前面的大头成本。

1. 一次请求批量读取活跃任务 runtime，序列化复用同一份结果；终态任务直接使用最终事实源，避免无效 Redis I/O。
2. 为任务类型维护只读列表/计数快照，避免每次状态轮询遍历所有业务任务并执行上下文补全；列表排序和隐藏任务规则必须保持一致。
3. 缓存按业务域版本失效，键必须包含 compact，修复当前 compact/full 共用缓存的独立正确性缺陷。
4. 用轻量摘要提供轮询所需统计，文件详情按需读取；成功/失败总数必须基于完整数据维护，不能从截断的预览文件推算。
5. 必要的同步 Redis/序列化工作移至工作线程，或改为异步批量读取；同时验证并发读取快照，避免把可变任务对象直接跨线程遍历。

验证 Redis 命令数、终态任务读取次数、compact/full 交替请求、失败重试历史、多文件任务计数，以及下载进度持续变化时的缓存刷新。

### 第三批：任务中心摘要分页

涉及 `task_center_service.py`、`task_center_materialization_service.py`。

旧摘要路径先 `_build_all_items` 聚合全量任务，再筛选、计数、分页；`limit=10` 不能限制前面的计算量。源码提供物化摘要开关，容器配置未设置；运行进程实际开关和物化完整性需在切换前复核。

1. 对比物化表与现有读路径的总数、各域/状态计数、排序及条目字段。
2. 验证 processing、待重试、冲突、隐藏/替代任务和重启恢复的刷新完整性。
3. 在一致性通过后使用物化摘要做数据库筛选、排序、分页，补齐事件更新与版本失效，再切换正式路径。空结果必须能表达真实空集合，不能无条件触发全量聚合。

### 第四批：统计与共享调度

涉及库存统计路由、`library_manager.py`、慢请求日志。

- `ensure_stats` 虽然声明为 async，内部仍有同步索引读取与磁盘健康检查；将阻塞工作移出事件循环，健康状态按独立短期缓存维护。
- 增加事件循环延迟采样，记录数据库/Redis/工作线程等待及业务计算分段；GET config 本身在线程池执行，同期变慢的精确原因需要这些证据判定。
- 不通过加多个应用进程解决共享内存任务引擎的一致性问题。
- 将成功慢请求显示为“请求耗时告警”，错误显示为“请求失败”，保留 status、耗时、request_id。500ms 阈值保持不变。

## 验收与发布

以下是建议验收目标，不是已实现结果：

- 以约 7 万作品位置建立不带 cProfile 的冷读基线；第一批冷读耗时至少下降 50%，热读 P95 小于 100ms。若仍超过 500ms，继续解决重建成本，不以抬阈值结案。
- HTTP/百度状态及任务摘要在代表性任务规模下，稳定状态 P95 小于 200ms；并发下载、索引更新及页面轮询时 P95 小于 500ms。记录样本量、冷热缓存和任务规模。
- 下载状态 Redis 读取次数不随终态任务数量增长；compact/full 结果不互串，计数与详情一致。
- 原始慢请求场景复测，并能通过分段日志解释剩余耗时；移动/删除后不出现可操作的陈旧路径，多位置数据不丢失。
- 各批按业务模块分别验证、分别提交。当前工作区已有大量修改，实施前必须核对既有 diff，不能覆盖或把它们当作本次修复提交。
- 发布是独立操作：按生产发布规则检查实际基线、备份、处理任务数量、哈希及健康状态。本文不授权上线。

### 聚合算法基准

可重跑工具：`tools/benchmark-circle-aggregation.py --samples 7`，使用项目后端 venv 执行。

- 69,932 个合成作品位置、1314 个社团；新旧完整快照结果逐次比较一致。
- 旧 `_build_snapshot` 来自运行时指定的 Git 基线（默认 HEAD），在当前模块中执行，共用当前辅助函数；这是快照算法对照，不是整个历史版本端到端对照。
- 同轮 7 个冷样本，旧实现毫秒：`486.20, 495.57, 463.00, 484.23, 440.00, 444.77, 437.60`；新实现：`234.67, 292.64, 224.72, 231.50, 255.24, 222.10, 199.92`。
- 冷构建中位数 `463.00ms → 231.50ms`，本轮约下降 50.0%；210 个热分页样本 P95 为 `0.2243ms`。更早一轮中位数改善约 44%，存在运行波动，不能以单轮结果承诺生产达标。
- 数据库、健康检查和网络均使用替身；不能与生产带 cProfile 的 11.9 秒直接比较，也不能据此认定线上端到端已小于 500ms。
