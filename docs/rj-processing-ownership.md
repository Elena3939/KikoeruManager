# 同 RJ 处理权与合集拆分

## 2026-11-13 事故证据

生产主机 Elena，容器 elena39-kikoerumanager。调查仅查询 PostgreSQL MCP 和读取应用日志，未修改生产数据或重跑任务。

父任务 58c44916-97fc-4c99-9dfa-0beb7981107d 处理 RJ01705625.7z。日志证实它在 16:22:40 标记 RJ01705625 正在处理；嵌套解压后，16:33:04 才发现 RJ01705625、RJ01759849 两个独立作品。

16:33:06 派发 RJ01705625 子任务 34b9d2cc-7ec9-4675-b7f3-dff0f12160d1 时，父任务仍持有 RJ 标记。子任务预检命中该标记，写入 conflict_works：conflict_type=DUPLICATE、existing_path=正在处理中、status=PENDING，随后进入 waiting_manual。父任务到 16:33:15 才完成。问题记录没有真实库存目标，界面因此只能展示没有可合并库存目录的说明。

16:33:07 的日志还显示，子任务被移出业务并发槽时取消了 RJ01705625 标记。它从未获得该标记，实际清掉的是父任务的占用。

根因是 RJ set 无法表达持有者，加上父子派发没有处理权交接。原查重还在异步库存查询后才添加标记，两个并行预检可能一起通过。历史清理对 waiting_manual 或仍有文件的记录选择保留，所以错误问题记录不会随着父任务完成自动消失。

## 处理规则

- 引擎维护 RJ 到任务 ID 的映射，取得和交接在事件循环内同步完成。取得处理权在库存异步查询之前，同任务允许重入。
- 正常入库和人工确认后的重试共用处理权；人工确认仅改变库存冲突判断，不允许两个任务同时处理同 RJ。
- 解压后才发现合集时，父任务切换为整包身份。每个子任务入队前，父任务已有的对应 RJ 处理权直接交给该子任务；父任务收尾不能释放已交接的处理权。
- 子任务登记失败或派发取消时，只释放尚未进入引擎的子任务处理权，保留已搬出的载荷。已入队的子任务由自己的生命周期收尾。
- 竞争任务以 pending 和“等待同 RJ 任务完成”展示，rjcode_wait 记录 RJ 和占用任务 ID。等待协程保留当前执行上下文，让出业务名额，不反复查库、不重新解压；处理权变化通过进程内事件唤醒。取消检查间隔最多 0.5 秒，重新竞争业务名额只检查内存容量。
- 正常查重恢复后重新查询直接库存；已有文件夹流程在取得处理权后再查直接和关联作品。只有真实库存冲突才生成问题记录。
- 取消、清理和任务结束按持有者 ID 释放全部处理权，不依赖可能已经变化的 task.rjcode。仍有执行协程的暂停任务保留处理权，避免另一任务同时进入同 RJ。
- 进程内处理权随进程结束消失，已持久化任务恢复执行时重新取得；不按时间删除 PostgreSQL 来源占用记录，不删除历史问题作品。
