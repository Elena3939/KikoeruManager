# PikPak 认证恢复与直链解析

## 保存凭据恢复

- `pikpakapi` 的 `encoded_token` 只序列化 access token 和 refresh token，不保存用户 ID；重新创建客户端后，`user_id` 默认为 `None`。
- SDK 的 `get_download_url()` 先调用 `/v1/shield/captcha/init`，其中 `meta.user_id` 必须是字符串。未补齐用户 ID 时会发送 JSON null，服务端返回 `proto: invalid value for string type: null`。
- `HttpDownloadService._pikpak_client()` 在读取保存凭据后，从 access token 的 JWT payload 取字符串 `sub` 补齐 SDK 用户 ID，覆盖普通客户端和跳过重复 token 检测的下载客户端。这里只恢复现有凭据的请求字段，不把未验签 payload 当成本地授权依据；认证仍由 PikPak 服务端执行。
- 用户标识缺失或格式不正确时，关闭客户端并明确报错；不发送含 null 的验证码请求，不输出 token，也不为恢复字段额外登录。

## 重试边界

- `null` 字符串参数错误不属于文件转存未就绪，立即报错，不能靠增加等待或重新转存解决。
- 明确的文件未就绪、转码或审核状态，仍在同一转存文件 ID 上重试，最多 24 次，退避上限 15 秒。
- 每个文件的直链解析总时限为 300 秒，包含 SDK 内部请求重试、重新登录及退避；超时取消当前请求并给出明确错误。
- 仅认证类错误允许重新登录，网络断连或文件状态错误不触发密码登录。
- 保留显式 API 代理配置，不在失败时自动改成直连。

## 诊断与验收

- 先分清分享枚举、转存、文件 ID 匹配、验证码初始化、文件详情和实际下载各阶段；容器健康与状态接口 200 不能替代业务验收。
- 2026-11-10 的只读线上对照：同一账号与文件，SDK 原始客户端的验证码请求返回 null 参数错误；仅恢复 `user_id` 后验证码请求成功。随后代理链路出现超时，直连对照的验证码和文件详情均为 200，并返回下载直链。两个问题独立，不能把网络超时继续归为转存等待。
- 回归测试使用真实 SDK 和 `httpx.MockTransport`，确认有效保存凭据无需重新登录，验证码请求携带用户 ID，且能够取得直链；另覆盖无效用户标识、null 参数立即失败、SDK 请求总超时取消及真正文件未就绪的同 ID 重试。
- 本地修复和只读探测不等于部署，也不等于当前线上任务已恢复；部署后仍须对真实任务进行解析与下载验收。
