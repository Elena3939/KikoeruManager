## South+ Cookie 补测与合并搜索实验

用户补充 Cookie 后，在本地使用现有代理实测。Cookie 已保存至 `data/config/config.yaml`，未写入模板、源码或报告。测试期间暂时暂停后台 South+ 领取，等待已有请求完成并再冷却 10 秒，结束后等待 10 秒再恢复原启用状态，避免测试进程与后台分别限速造成撞请求。

首先发现并修复了实际配置兼容问题：当前 South+ 代理填写的是没有协议的 `host:port`，原实现直接传给 httpx，会在发出 HTTP 之前抛出 `ValueError`。现与 DLsite / ASMR 保持同一约定，缺少协议时补 `http://`；显式 HTTPS 代理保持原值。连接池也使用规范化后的地址作为键，等价写法共享连接。

修复后真实逐个搜索：

| RJ | HTTP | 结果条数 |
| --- | ---: | ---: |
| RJ01248374 | 200 | 2 |
| RJ01256580 | 200 | 0，页面明确返回“没有查找匹配的内容” |
| RJ01256588 | 200 | 3 |

3 次搜索总耗时 **21.879 秒**，共建立 **1 条 TCP 连接**；从上次响应结束至下次请求开始分别为 **10.0029 秒、10.0105 秒**。没有 403/429。现有单实例锁同时约束连接测试与后台搜索，成功和异常都会从结束时间开始再冷却 10 秒。新增虚拟时钟测试覆盖这两条路径，相关测试共 **23 项通过**。这不是跨进程全局限速证明。

进一步实测站点 `method=OR`：同一请求用空格或 `|` 连接上述 3 个 RJ，两种写法均返回相同的 5 个帖子。按标题中的 RJ 归属、按帖子 ID 去重后，与三个单独搜索逐项一致，仍为 **2 / 0 / 3**。首次合并请求耗时 **3.294 秒**；第二种写法含等待前次请求结束后的 10 秒冷却，共 **10.401 秒**。

这里可行的优化是 **减少搜索次数**：本样本从 3 次搜索变为 1 次，单组测量从 21.879 秒变为 3.294 秒。单组计时有首请求无需等待、顺序执行及远端缓存的影响，不能直接承诺持续吞吐提升 6.6 倍；若长期每批稳定容纳 3 个 RJ 且无需翻页，理论搜索吞吐约为单条方式的 3 倍，站点请求仍保持 10 秒冷却。

**合并搜索目前只完成真实可行性验证，尚未接入后台批量领取与落库。** 接入前必须处理结果分页、关键词上限、标题未携带 RJ 的归属问题，以及未完整覆盖时不能给整批写 `miss`。本次还实证了现有匹配函数不能直接用于批量归属：帖子 URL 的 `keyword-...` 会回显全部 RJ，若拿 URL 匹配，会把 3 个作品都误判为各命中 5 条。正确性对照已排除这个查询回显，只使用标题 RJ 和帖子 ID；不能把初步解析结果当作验收。

本次新增的生产逻辑改动仅为代理协议补全，10 秒冷却保持不变；已通过根目录 `start-all.bat` 重启本地服务。真实证据保存在忽略目录 `data/run/south-plus-20261019/`：`result.json`、`batch-result.json`、`batch-comparison.json` 和原始页面；其中 `batch-result.json` 是暴露 URL 回显误归属的初步结果，最终应以 `batch-comparison.json` 为准。以下历史章节“South+ 未测”指补 Cookie 之前，不再代表当前结果。

## 百万规模的容量决策

先减少无意义扫描，再讨论语言迁移。以单出口当前节奏估算理论下限，不包含网络延迟、错误和重试：

| 来源 | 约束 | 百万量级意味着什么 |
| --- | --- | --- |
| South+ | 响应后至少 10 秒间隔 | 百万搜索至少 115.7 天；无法靠增大线程数解决 |
| YAAS | 全局约 0.34 秒/HTTP；每 RJ 至少两个根目录搜索 | 百万 RJ 至少 200 万请求、约 7.9 天；命中后的目录枚举继续增加请求 |
| ASMR.one | 单实例元数据 2 QPS | 百万次请求至少 5.8 天；完整命中核对通常还需音轨请求 |
| DLsite 特典 | 最大 500 RJ 合并 product/info | 应按不同候选 RJ 计请求，不按原作数重复扫重叠编号区间 |

因此 YAAS 当前 missing 每 6 小时重探若覆盖百万全库，容量上根本不成立。本轮没有把这个全局调度策略悄悄改掉，建议按以下明确规则继续落地：

1. 页面只读 PostgreSQL/Redis 快照；用户明确刷新、近期新增作品、最近活跃社团优先入队。冷历史记录不因打开列表而全量刷新。
2. miss 首次 6 小时，连续稳定 miss 逐步退避到 1/3/7 天；用户明确刷新可提升优先级；error/限流与 missing 分开，不据此写不存在。TTL 需要按站点和业务的新资源出现速度设置。
3. YAAS 目录 list 按目录缓存并合并并发请求，同目录多个 RJ 共享完整枚举；保持分卷完整性检查，不能只取搜索首项。该目录缓存本轮尚未实现。
4. 队列每来源独立调度、设置最大积压和每日请求预算；大库只有到期且进入活跃集的记录进入 ready 队列。监控最老任务年龄，避免用户刷新始终饿死普通任务。
5. HTTP/HTTPS 代理按出口身份与目标站限速，复用长连接；代理换地址不代表换出口 IP。多个进程时，将 ASMR 的实例级节奏提升为 Redis 共享限速；本轮 ASMR 尚不保证跨进程总 QPS。
6. PostgreSQL 是事实源，Redis 保存租约、短缓存和缓冲；持久结果唯一键、批量 upsert 和分页读取优先，避免为百万行创建完整 ORM 对象。特典继续使用现有 Redis dirty buffer 批量回写，并监控 stream 积压和落库延迟。

并发建议：保留特典 6 日期 worker，批量请求先按现配置运行；Anime 2、South 1、YAAS 2 已落地。提高并发必须同时观察有效结论/分钟、429/403、P95、连接池等待和队列年龄；出现限流应降低请求节奏，不能仅凭 CPU 空闲继续增加 worker。

## Go / Rust 决策

当前保留 Python asyncio。前轮 RaRo 采样 30 秒仅约 1.78 CPU 秒，主要是网络等待、请求放大和调度；本轮连接复用及请求去重已经能直接改善。换语言不会解除上面的外站请求预算。

未来只有在去重、连接复用、批量数据库操作完成后，仍测到解析/序列化长期占满 CPU，才抽出独立 worker。团队要降低开发成本可优先 Go；需要极低内存或明确 CPU 热点再考虑 Rust。两者都不建议现在整体迁移，也不建议为探测服务额外引入第二套事实数据库。

workInfo/tracks 的 perf 字段是函数调用数，不等于精确 HTTP 数；tracks 在当前 INFO 日志下不可逐请求完整统计。完整任务没有底层 HTTP trace，不能仅凭日志宣称全程零 429；资源独立复测的 36 次全 200 有底层 trace 支持。日志匹配必须识别 HTTP 状态，不能把 RJ 编号中包含“429”算作限流。

以上是被否决轮次的结论。后续已经验证并接入完整社团目录，实际将这个阶段降到约 141 秒，见本文开头；持久音轨缓存仍未实现。不能直接放开 QPS，否则会回到前轮快速失败的问题。
